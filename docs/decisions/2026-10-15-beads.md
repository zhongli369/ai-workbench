# 决策：不引入 Beads（gastownhall/beads）— REJECT

日期：2026-10-15 · 评估人：Agent C（Task Graph Engineer）· 对象：Beads 四大卖点 vs harness-core 现状
一句话理由：Beads 的四个卖点（持久任务依赖 / 未阻塞识别 / 多 Agent 认领 / 跨会话连续）在现有
Plan + Checkpoint + project 命名空间 + git worktree 上已有等价且经测试的机制，且仓库内无任何
真实缺陷证据；引入 Dolt 状态层将违反 harness 的 stdlib-only / 零常驻服务契约。
即日生效，不 clone、不安装、不试用、不建 `.beads`、不引入 Dolt。

## 四问四答（证据 = 文件:行号；验证 = 已运行测试）

**Q1 Plan 能否表达任务间依赖？** 能表达"单任务内的有序阶段"（线性前置）；不持有"多任务 DAG"。
- `harness-core/harness/plan.py:396-431`：`plan(task)` 为单任务入口；`phases`（`:412-416` 按 num 1..N）+
  `acceptance_criteria` + `checkpoint_hint`（`:424-430`，每个 phase 即一个 checkpoint stage 名）。
- harness-core 全文无 `depends_on/blocks/DAG` 原语（grep 0 命中）。
- 任务级依赖图由编排层承担：`workbench/.claude/skills/parallel-execution-optimizer/SKILL.md:16-38`
  （先写 dependency graph / lane matrix，再只并行互不碰撞的 lane）；DEEP 分级见 `workbench/CLAUDE.md:17`。
- 判定：够用。依赖图的真相源 = plan 文档 + 编排决策；持久化副本（Beads 的图数据库）是冗余状态层。

**Q2 Checkpoint 能否跨会话恢复任务进度？** 能，且是明确设计目标。
- `state.py:111-149` crash marker（begin 后崩溃可定位在飞 stage）；`:159-195` append-only save（parent_id 谱系）；
  `:252-259` load_latest/replay；`:261-288` verify（hash/谱系/阶段单调性三重校验）。
- 实测：`tests/battle/test_s04_resume.py:99-147` — 三 stage 进程在 stage3 前被杀，`checkpoint load` 返回
  last valid + active marker，精确从 stage3 恢复，敏感操作（oplog）未重复执行，链完整性 ok。
- 诚实边界（测试自述 `:18-20`）：CLI 提供机制，模型负责做恢复决策 — 与 Beads 同为"机制+决策"分工。
- 同类真实缺陷已闭合：跨项目同名 exec_id 串写 → `docs/multi-project.md:64-83` 记录并修复
  （`state.py:92-107` project 命名空间 `<project>~<exec>.jsonl`，`~` 不在 `_safe_id` 字母表，永不冲突）。

**Q3 多个原生子 Agent 能否明确拥有各自任务？** 能。所有权 = execution_id + project 命名空间 + worktree/branch。
- 作用域解析：`cli.py:22-52`（`--project-id` 优先，显式 `--cwd` 推导）；`project_id.py:66-87` 五级身份链。
- 隔离实测：`tests/multiproj/test_case_a_isolation.py:41-98`（A 全量操作后 B 树逐字节不变、无 harness 残留、
  A 的 manifest 不含 B 路径）、`:134-139`（各 repo 仅持有自己的 refs/harness）；命令入口 `cli.py:129-175`。
- worktree 隔离是本仓库真实实践：本任务即运行在独立 worktree；历史合并 `cf1fbb2`（Agent A）、`c8b0524`（Agent C）。
- 完成归属：`verify.py:556-575` `can_claim_done` 把"完成"钉死在该 exec_id 的证据链上（exit 0 才算可宣称完成）。

**Q4 是否存在真实的并行错误认领 / 跨会话遗漏问题？** 无证据。
- `docs/incidents/registry.json`：4 个真实事故（权限探测、verify 根目录、pycache 溯源、机器路径泄漏），
  无一属于任务认领/遗漏类。
- 唯一同类真实缺陷 = 跨项目 exec_id 串写（见 Q2），已修复且有回归测试；本轮复核后仍全绿。
- 已知诚实边界（非缺陷）：`tests/battle/test_s03_fake_completion.py:188-213` skip 不撤回旧 pass（显式标注）；
  `:215-236` 完成门是"可查询"而非"可强制"（无 hook 强制调用）。
- 按判据：无证据 = 无问题。

## 门槛核对与结论

- 门槛（提供现有工作台不能可靠实现的真实能力 + 不破坏现有状态体系 + 不默认启动服务）：**不满足**。
- 上游自证弱点：`bd ready --claim` 并发下非事务（两个并发 claim 拿到同一 bead，gastownhall/beads#5998）；
  Beads 依赖 Dolt 后端（`bd doctor` 会拉起本地 Dolt server）——"多 Agent 认领"在共享 ledger 上
  并不比 worktree 分配模型更可靠，且直接新增常驻服务与数据库依赖。
- 冗余风险：Beads 的任务状态/依赖/认领与 Plan 阶段 + Checkpoint 链 + project 命名空间三重重叠；
  该仓库历史上已因"第二路径"判过 D-class 冗余（`plan.py:11-22`，feedback adaptation 被拒先例）。
- **结论：REJECT。** 若未来出现有证据的真实缺口（如多任务图查询），优先做 Plan/Checkpoint 的最小扩展，
  不引入外部数据库或第二状态层。
